# 第1部 基本アーキテクチャ

## 前提となる規模

公式メタデータCSV(2026-08-22版)を取得して確認した実測値。

| 項目 | 値 |
|---|---|
| 著作権切れの作品 | 17,352件 / 著者1,021人 |
| 複数人物が紐づく作品(翻訳者など) | 1,102件 |
| 本文ファイル | zip(1作品1ファイル)、Shift_JIS + CRLF |
| メタデータCSV | zip 2.0MB / 19,502行 |

## 全体構成

```
[ビルド時] 公式CSV(全作品分が1リクエスト)
   → 著作権切れのみ抽出 → 索引データ
        ├→ Astro が静的ページ生成(トップ → 行別著者一覧 → 著者ページ)
        ├→ Pagefind が検索インデックス生成
        └→ 作品ID別シャードJSON(エッジ関数用)

[リクエスト時] /works/{作品ID} のみ動的
   → エッジ関数(Astro on-demand + Pages Functions)
       ① KVを参照 → ヒットならそのテキストを使う
       ② ミスなら: シャードJSONでzipのURLを引く
                  → zip取得 → deflate-raw展開 → Shift_JIS→UTF-8 → KVに保存
       ③ 記法パーサーでHTML化(本文と底本情報を分離)
   → ブラウザが読み方モードに応じてCSSで描画
```

技術スタックは Astro(hybrid) / Tailwind CSS / TypeScript、ホスティングは Cloudflare Pages(+ Pages Functions + Workers KV)。

## なぜこの構成なのか

### 出発点: 作品数は多いが、作品単位で取得できる

17,352作品という規模は個人サイトの想定を超えるが、青空文庫は**作品ごとに独立したzipを配布している**(羅生門で7,191バイト)。もし全作品まとめた一括zipしか無ければ、事前にどこかへ展開して置くしかなく、後述するミラーの問題を避けられなかった。作品単位で取れることが、この設計全体の前提になっている。

### 静的と動的の境界は、取得コストで決まる

全作品を静的生成しようとすると、ビルドのたびに**17,352回のリクエスト**を青空文庫に投げることになる。これは公式が避けるよう求めている一括クロールにあたる。加えてプラットフォーム側にも硬い上限がある。

- **Cloudflare Pages のファイル数上限は無料20,000 / 有料100,000**。17,352作品ぶんのHTMLは、他のアセットと合わせて無料枠の上限に張り付く
- **ビルドは20分でタイムアウト**。17,352回の取得を20分で終えるには秒間15回のアクセスが必要で、これは明確に迷惑な速度

**本文の静的生成は成立しない**。

一方メタデータは全作品分が**2MBのzip 1個**、つまり1リクエストで手に入る。五十音ブラウジングのページ群はこれだけから導出できる。

つまり境界線は「1リクエストで足りるか、17,352必要か」で引かれている。恣意的な線引きではない。

オンデマンドにしても負荷と費用が問題にならないのは、**青空文庫の本文が公開後ほぼ改訂されない**ため。一度取得して保存すれば二度と取りに行く必要がなく、公式サーバへのアクセスは作品あたり実質1回に収まる。費用も作品数ではなく実際に読まれた回数に比例するため、17,352作品を載せても10作品のときと変わらない。

### 出所は公式サイトに一本化する

**却下した案: ミラー経由での取得。** 当初は `aozorahack/aozorabunko_text` を jsDelivr 経由で取得する設計だった。しかし調査の結果、公式FAQが案内する `aozorabunko/aozorabunko` は**現在404**(orgはあるが public repos = 0)、`aozorahack.net` のAPIサーバもDNS解決しない。代替の `aozorabunko_text` は**2023年3月で更新が停止**しており、以降の著作権切れ作品430件(更新含め537件、全体の2.5〜3.1%)が欠落する。

これは事故ではなくミラーの構造的性質で、同期し続けなければ必ず陳腐化する。残る選択肢は「他人のミラーに依存して陳腐化する」か「自分で維持して運用義務を負う」かのどちらかで、鮮度が前提・省運用が要件である以上どちらも取れない。

**出所を公式1つに絞れば、維持すべきコピーが存在しないため鮮度が自動的に保たれる。** 副次的に、メタデータと本文の出所が一致するため「CSVには載っているがミラーには無い」という不整合が起きえない。

### 本文はテキスト版を取り、記法は自前でパースする

公式は同じ作品をテキスト版(zip)とXHTML版で配布している。

**却下した案: 公式XHTML版。** ルビがマークアップ済みでzipでもないため一見有利だが、実物(羅生門)を検証したところ縦書きレイアウトの実験と衝突した。

- **段落が存在しない**。`<p>` が0個で、本文全体が `<div class="main_text">` 内に `<br />` 62個で区切られているだけ。段組みの列分割はブロック要素の境界を手がかりにするため、字下げも列の切れ目も制御できない
- **外字が画像**(`<img src="../../../gaiji/...png" class="gaiji" />`)。フォントサイズに追従せず行内で浮く。相対パスなので自サイト配信では壊れ、直リンクすれば毎回公式サーバを叩く。テキスト版は `※［＃「てへん＋丑」、第4水準2-12-93］` と面区点番号を持つのでUnicodeへ変換して本物の文字として組める
- **Shift_JISなのは同じ**で、文字コード変換の手間は減らない
- `aozora.css` と jQuery を読む完全なHTML文書のため、`main_text` の抽出・不要参照の除去・`<rb>`(HTML標準から削除済み)の書き換えが必要。パースから逃げられるわけではなく、対象が記法からHTMLに変わるだけ

底本情報が `class="bibliographical_information"` として整理されている点は優れており、横書きの一般的なリーダーなら妥当な選択肢だった。**縦書きで組版を制御したいという目的が、テキスト版を要求している。**

なお、zipの展開は外部ライブラリなしで済む。青空文庫のzipは1ファイル構成なので、ローカルファイルヘッダを読んで deflate ストリームを `DecompressionStream('deflate-raw')` に渡すだけでよい(検証済み)。

### 取得したものは Workers KV に保存する

**却下した案: Cache API (`caches.default`)。** キャッシュがWorkerのバージョンで区切られるため**デプロイのたびに空になる**。ビューア実験が主題でデプロイ頻度が高い本プロジェクトとは相性が悪い。加えてデータセンター単位でしか共有されず、アクセス元が分散すると取得が繰り返される。

KVはデプロイ・再起動をまたいで永続し、グローバルに複製される。公式ドキュメントも「大量の読み取りと同一キーの繰り返し読み取り」にはKVを推奨している。R2(無料枠10GB)も検討したがGB級オブジェクト向けで、数十KBのテキストには過剰かつ読み取りが遅い。KVはホットキーで0.5〜10ms。

**保存するのはパース済みHTMLではなく、UTF-8変換済みの生テキスト。** パーサーは本プロジェクトの主題であり頻繁に書き換わる。パース結果を保存すると1行直すたびに全キャッシュが無効化され取り直しになる。遅いのはネットワーク取得でパースはCPU処理なので、生テキストを保存すれば遅い部分だけを回避でき、パーサーの変更に影響されない。

### 探す導線は静的ファイルだけで完結させる

五十音ブラウジング(トップ → 行別著者一覧 → 著者ページ)は、CSVの読み仮名から機械的に生成でき、**著者ページまで全て静的生成できる**。そのため索引データをクライアントに丸ごと送る必要がない。

検索には [Pagefind](https://pagefind.app/) を使う。インデックスは語ごとに分割された静的ファイルとして出力され、ブラウザは該当する破片だけを取得するので、作品数が増えても転送量が増えない。検索がCDN上の静的ファイルで完結し、サーバー・外部サービス・APIキーを必要としないため、低コスト・省運用の要件に合う。SaaS(Algolia等)はアカウントとAPIキーの管理、索引の同期処理が増え、無料枠は一定期間の未使用でアプリケーションが削除される運用リスクもあるため採らない。

### まとめ: 各処理をどこに置くか

以上の結果、各処理は「入力が揃う最も早い時点」かつ「一度で全員が再利用できる層」に配置される。

| 処理 | 場所 | 理由 |
|---|---|---|
| メタデータ整形・ブラウジング生成 | ビルド時 | 全作品分が1リクエストで揃う |
| 本文取得・文字コード変換 | エッジ + KV | 対象は読者が開くまで不定。内容は不変なので保存すれば1回 |
| 記法のパース | エッジ(毎回) | パーサーを頻繁に書き換えるため結果を保存しない |
| 縦書きレイアウト | ブラウザ | 画面サイズとモード選択が読者ごとに違う |

事前計算が作品数に比例しないため、作品数が増えてもコストが増えない。外部依存は公式サイト1つだけで、維持すべき自前の資産(ミラー・検索サービス・DB)を持たない。

# 第2部 詳細設計

## データの出所

- メタデータ: `https://www.aozora.gr.jp/index_pages/list_person_all_extended_utf8.zip`
- 本文: CSVの `テキストファイルURL` 列が指すzip(URLはCSVに入っているので組み立て不要)

## コンテンツモデル

```
Work   id / title / titleKana / sortKana / cardUrl / sourceUrl
       contributors: [{ personId, role }]   role = 著者|翻訳者|校訂者|編者|その他
Person id / name / nameKana / sortKana
```

- 作品は複数の人物を持つ(翻訳作品など1,102件)ため、1作品1著者のモデルは取れない
- ブラウジングと著者ページは `役割フラグ`=著者 を基準に構築。翻訳者・校訂者は作品ページのクレジットに表示
- 著作権フラグは索引生成時にフィルタ済みのため保持しない
- テキストURLが空・外部サイト設置の作品(著作権切れで計9行)は除外

## サイト構成

| URL | 内容 | 生成 |
|---|---|---|
| `/` | 五十音へのリンクと検索窓 | 静的 |
| `/authors/{行}` | その行の著者一覧 | 静的 |
| `/authors/{人物ID}` | その著者の作品一覧 | 静的 |
| `/search` | 作品名・著者名の検索 | 静的 |
| `/works/{作品ID}` | 本文をビューアで表示 | オンデマンド |

## メタデータ索引

使用する列: `作品ID` `作品名` `作品名読み` `ソート用読み` `作品著作権フラグ` `図書カードURL` `人物ID` `姓` `名` `姓読み` `名読み` `姓読みソート用` `役割フラグ` `テキストファイルURL`

生成した索引はリポジトリにコミットする。`npm run update-index` を手動実行し、差分を確認してからコミットする。

1. CSVを取得し著作権フラグ「なし」を抽出
2. 作品IDでグループ化し複数人物を `contributors` にまとめる
3. テキストURLが無い/外部ホストの作品を除外
4. Work / Person と、作品IDでシャーディングしたJSONを出力

**コミットする理由**: 代替案はビルド時に毎回CSVを取得する方式だが、静的生成である以上どちらも鮮度は「ビルド時点の最新」で、差は更新が手動か自動かだけ。コミットする方式はビルドが再現可能で、更新時に差分を確認できるため意図しない大量変更に気づける。定期自動更新が要るなら後からGitHub Actionsを足せる。

**シャーディングする理由**: zipのパスは `cards/{人物ID}/files/{作品ID}_ruby_{連番}.zip` で末尾の連番が予測できず、作品ID→URLの対応表が避けられない。一方エッジ関数が毎リクエストで17,352件を読むのは重いため、該当部分だけを読める大きさに分割する。

## 本文の取得

1. `テキストファイルURL` のzipを取得。**`User-Agent` を必ず付ける**
2. ローカルファイルヘッダを読み、deflateストリームを `DecompressionStream('deflate-raw')` で展開
3. `TextDecoder('shift_jis')` でUTF-8化
4. Workers KV に保存

いずれもWeb標準APIのみで、Cloudflare Workers 上で動作することを確認済み。

**`User-Agent` が必須**: 青空文庫のサーバは UA の無いリクエストを受け付けず、Workers 上では接続エラーとして現れる。どこからのアクセスかを名乗るのは外部サイトを利用する側の礼儀でもある。

## キャッシュ

Workers KV に、パース前のUTF-8変換済みテキストを保存する。キーは作品ID。

- 無料枠 1GB / 読み10万回・日 / 書き1,000回・日
- 書き込みは「未取得の作品が初めて開かれたとき」だけなので実質制約にならない

### 長編作品とCPU時間

**実測(ドグラ・マグラ / 47万字 / zip 412KB)**

| 処理 | 時間 | 概算 |
|---|---|---|
| 取得 | 420 ms | ネットワーク待ちのためCPU時間には**数えられない** |
| zip展開 | 12 ms | 約 30 KB/ms |
| Shift_JIS変換 | 3 ms | 約 300 KB/ms |
| パース | 48 ms | 約 1万字/ms ← **支配項** |
| **CPU合計** | **63 ms** | |

Workers無料枠のCPU上限は **10ms**(有料は既定30秒、最大5分)。パースが約1万字/msなので、無料枠で扱えるのは展開・変換ぶんを差し引いて**数万字程度**が限界。

作品30件を無作為抽出したzipサイズ分布との対応:

| 分位 | zip | 概算CPU | 無料枠10ms |
|---|---|---|---|
| 中央値 | 5.8 KB | 約1 ms | ○ |
| 上位25% | 12.6 KB | 約2 ms | ○ |
| 上位10% | 135 KB | 約20 ms | ✗ |
| 最大級 | 412 KB | 63 ms | ✗ |

**上位1〜2割の作品は無料枠では扱えない。**

**超過時の挙動**: エラー1102 "Worker exceeded resource limits" が返る。応答が返らないのではなくエラーページが表示される。影響は当該リクエストのみで、他の作品や他の読者には波及しない。単発の超過には多少の猶予があるが、恒常的に超える長編は確実に落ちる。

**メモリ**: 1102はCPUだけでなく128MBのメモリ超過でも発生する。メモリ上限は有料プランでも変わらず、isolate単位で複数リクエストが共有するため、長編の同時アクセスが重なると危ない。

**方針**: 当面は有料プラン($5/月)でCPU上限を回避する。設計変更を伴わないため。メモリ側で行き詰まった場合は下記の分割配信に移行する。

**本番での確認(2026-09-03)**: 有料プランで公開し、想定していた最長級の作品が実際に通ることを確かめた。設計段階では見積もりだけで、実証はできていなかった。

| 作品 | 文字数 | 結果 |
|---|---|---|
| 羅生門 | 6,483字 | 11ページ |
| 大菩薩峠 第一巻 | 68,835字 | 135ページ |
| **ドグラ・マグラ** | **448,783字** | **733ページ** |

メモリ(128MB)の方は、同時アクセスが重なる状況をまだ試せていない。

### 長編への打ち手(将来)

現設計は取得・展開・変換・パース・送信・ブラウザの組版まで、すべてが本文長 N に対して O(N) で、定数倍で切る仕組みを持たない。行き詰まった場合の選択肢:

- **分割配信**: 作品を区間に分けて配る。KVに**生テキスト**を保存しているため、任意の範囲を切り出して必要な部分だけパースできる(パーサーは行単位の走査なので `parse(lines[a..b])` が素直に書ける)。パース済みHTMLをキャッシュしていたらこの道は塞がっていた。ただしURL・ビューア・読書位置がいずれも「作品全体が1ページ」を前提にしているため、ビューア設計に波及する
- **処理をブラウザに寄せる**: エッジはzipを取得してKVに置くだけにし、展開・変換・パースをブラウザで行う。`DecompressionStream` も `TextDecoder` もブラウザで動くため、パーサーのコードはそのまま使える。エッジのCPU消費がほぼ消える一方、サーバでHTMLを組まなくなるため、JavaScript無効では読めず検索エンジンのインデックスも不確実になる

いずれも現設計から移行可能で、いま決め打つ必要はない。

## 検索

作品名・著者名(読み仮名含む)を対象とする。作品ページはビルド時に存在しないため、HTMLのクロールではなくNode APIの `index.addCustomRecord` にレコードを直接渡す。

| 項目 | 内容 |
|---|---|
| `url` | `/works/{作品ID}` |
| `content` | 作品名・作品名読み・著者名・著者名読み |
| `language` | `ja` |
| `meta` | 表示用の作品名・著者名 |

日本語は `Intl.Segmenter` でクエリ分割される。活用形の吸収はないが、対象が固有名詞なので影響は小さい。本文の全文検索は1.6GB規模になり別物のため想定しない。

## ディレクトリ構成(たたき台)

```
src/lib/      aozora/ (記法パーサー)  content/ (zip展開・文字コード・KV)

src/components/viewer/

```

# 第3部 実装計画

## 公開

Cloudflare Workers に公開している。

| | |
|---|---|
| URL | https://viewer.hibara428.dev |
| | https://vertical-text-viewer-app.hibara428.workers.dev(従来のURLも生かしている) |
| プラン | Workers Paid。無料枠のCPU上限10msでは上位1〜2割の作品が落ちるため |
| KV | `WORK_TEXT`(本文のキャッシュ)。`SESSION` は Astro が要求するもので、初回デプロイ時に wrangler が自動作成した |
| アセット | 18,422ファイル / 76MB(圧縮1.2MB) |

独自ドメインと `workers.dev` の有無は `wrangler.jsonc` の `routes` / `workers_dev` で決まる。コンソールでの操作は要らない。

**ただし wrangler が読むのは `wrangler.jsonc` ではない。** ビルド時に `dist/server/wrangler.json` が生成され、そちらが使われる(`.wrangler/deploy/config.json` がその旨を指している)。設定を変えたら**必ずビルドし直す**こと。古い生成物のまま `wrangler deploy` すると、設定が反映されていないように見える。

> この落とし穴で一度誤診した。`routes` を足した直後に古い生成物を見て「設定ファイルに書いても効かない」と結論し、`--domain` をデプロイコマンドに埋め込む回避策を入れかけた。ビルドし直せば `routes` も `workers_dev` も正しく引き継がれる。

**アセットのファイル数が上限に近い。** Cloudflare の静的アセットは20,000ファイルまでで、いま18,422。うち**17,393(94%)が検索索引**で、青空文庫の作品が増えるたびに上限へ近づく。行き詰まったら索引の持ち方を変える必要がある。

```
npm run build && npx wrangler deploy
```

### 自動デプロイ

`main` への push で Cloudflare の Workers Builds がビルドして公開する。手元からの
`npm run build && npx wrangler deploy` も引き続き使える。

**この設定はダッシュボードにしか存在しない。** wrangler から設定する手段はなく、
`wrangler.jsonc` の Custom Builds も Workers Builds には効かない。リポジトリから追えないため、
入力した値をここに控えておく(Worker の Settings → Builds)。

| 項目 | 値 |
|---|---|
| Git repository | `hibara428/vertical-text-viewer-app` |
| Git branch | `main` |
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy`(既定) |
| Non-production branch deploy command | `npx wrangler versions upload`(既定) |
| Root directory | 空欄 |

`main` 以外のブランチへの push ではバージョンがアップロードされるだけで、本番のトラフィックは動かない。

**Build command を空にしてはいけない。** 上に書いたとおり wrangler が読むのはビルドで生成される
`dist/server/wrangler.json` で、検索索引の生成も `npm run build` に含まれている。

Node のバージョンは `.node-version`(24.20.0)が読まれる。ビルドイメージにあらかじめ入っているのは
22.23.2 と 24.18.0 のため、24.20.0 は毎回ダウンロードされる。ビルド時間が気になるなら
`.node-version` と `package.json` の `engines` を 24.18.0 に合わせるとキャッシュに乗る。

## ロードマップ

1. **通信経路の検証** — 作品IDを決め打ちで zip取得→展開→変換→パース→表示(索引・KVなし)
2. **メタデータ索引** — CSVから索引を生成し、作品ページが索引を引いて動くようにする
3. **五十音ブラウジング** — トップ→行別著者一覧→著者ページ→作品ページの導線
4. **検索** — Pagefindのインデックス生成をビルドに組み込み、検索UIを追加
5. **KVキャッシュ** — 取得した本文をKVに保存
