# ビューア設計

[docs/requirements.md](./requirements.md) の「ビューア」の詳細設計。システム全体の設計は [docs/design.md](./design.md) を参照。

## 青空文庫記法パーサー

zipを展開しUTF-8に変換したテキスト([docs/design.md](./design.md) 参照)を入力とし、HTMLに変換する。

### 入力テキストの構造

実データ(羅生門、71行)で確認した構造。

```
 1  羅生門                          ← タイトル
 2  芥川龍之介                      ← 著者
 3
 4  ------------------------------  ← 記号説明ブロック開始
    【テキスト中に現れる記号について】
    《》：ルビ  ｜：ルビの付く文字列の始まりを特定する記号 …
16  ------------------------------  ← 記号説明ブロック終了
17
18  　ある日の暮方の事である。…      ← 本文
    :
58  底本：「芥川龍之介全集1」…       ← 底本情報
    入力：平山誠、野口英司
    校正：もりみつじゅんじ
```

- 冒頭のタイトル・著者はメタデータとして既に索引にあるため、本文からは除去する
- 記号説明ブロックは**ハイフンの連続行に挟まれる**。読者に見せる必要がないため除去する
- `底本：` で始まる行以降が底本情報。本文から分離し、別フィールドとして保持する

### 出力形式

**HTML文字列**として出力する。ルビは `<ruby>` タグ、傍点は `<em>` 相当の要素、といったHTMLの標準的な表現に落とし込み、縦書き・段組みといったレイアウトはCSS側で制御する。

- ブラウザ本来の描画機能(ルビ配置、行分割、段組み)をそのまま使えるため、実装量が小さい
- 読み方モードの違いは、原則としてCSSの切り替えで表現する
- HTMLでは表現しきれないレイアウト要求が出てきた場合に、構造化データ(JSON)出力への変更を検討する

### 対応する記法

実データで網羅性を確認しながら詰める。

- ルビ: `｜語句《ルビ》`(`｜` は語句境界が曖昧な場合に使われる)
- 注記: `［＃「対象」に傍点］` のような形式。傍点・強調・見出し・字下げ・改ページなどがある
- 外字注記: `※［＃…］` の形式。後述
- 本文中で直接使えない文字: `《》［］〔〕｜＃※`

### 外字の扱い

外字は `※［＃「てへん＋丑」、第4水準2-12-93］` のように、字形の説明と**面区点番号**で表現される。この番号からUnicodeのコードポイントを導き、**本物の文字として組む**。

公式XHTML版はこれを画像(`<img class="gaiji">`)で表現しており、フォントサイズに追従せず縦書きの行内で浮く。テキスト版を選んだ理由の一つがこれなので([docs/design.md](./design.md) 参照)、画像にフォールバックはしない。変換表を持てないコードポイントに遭遇した場合は、注記中の字形説明を代替テキストとして表示する。

### 底本情報の扱い

分離した底本情報(底本名・入力者・校正者など)は、本文とは別に作品ページのフッター等で表示する。クレジットの保持は青空文庫の慣習として期待されている([docs/requirements.md](./requirements.md) の「コンテンツに関する制約」参照)。

## 読み方モード

読者が読書画面で切り替えられる。選択内容は localStorage に保存し、次回以降も維持する。

| モード | 文字の向き | 送り方 | 実現方式 |
|---|---|---|---|
| 1 | 横書き | 縦スクロール | `writing-mode: horizontal-tb`。通常のWebページと同じ |
| 2 | 縦書き | 縦スクロール | 後述 |
| 3 | 縦書き | 横ページめくり | `writing-mode: vertical-rl`。列が右→左に並ぶ性質をそのまま使い、画面幅単位でページ送りする。後述 |

### モード2の定義

縦書きは本来、列が右から左へ進むため横方向に伸びる。モード2では**列を画面幅で折り返し、折り返した「帯」を上から下へ積む**。読者はスマートフォンでも横スワイプを使わず、縦フリックだけで読み進められる。

```
   ← 列が右から左へ ←
┌─────────────────────┐
│ 三 二 一            │  帯1
├─────────────────────┤
│ 六 五 四            │  帯2  ↓ 縦にスクロール
├─────────────────────┤
│ 九 八 七            │  帯3
└─────────────────────┘
```

### モード2の実現方式(検証済み)

`writing-mode: vertical-rl` とCSSの段組み(multi-column)の組み合わせで実現できる。帯ごとの文字量計算は不要。

**要点は、制約する軸を間違えないこと。** 縦書きでは inline方向=縦、block方向=横 に入れ替わる。段組みの列は inline方向(＝縦)に積まれ、折り返しは block方向(＝横)のサイズで決まる。したがって:

```css
.body {
  writing-mode: vertical-rl;
  width: 100%;         /* block方向を画面幅に固定 → ここで折り返す */
  height: auto;        /* inline方向は内容に応じて伸ばす → 帯が縦に積まれる */
  column-width: 20rem; /* inline方向の寸法なので「帯の高さ」を指す */
  column-gap: 2.5rem;
}
```

`height` を固定して `width` を開放すると、要素が横に伸び続けて折り返さない(検証中に踏んだ)。

スマートフォン幅(390×844)でも意図通り動作し、横スワイプなしで縦フリックだけで読める。

### モード3の実現方式(検証済み)

読書領域を画面サイズの枠として固定し、その中で本文が右から左へ伸びる形にする。枠を横スクロールさせ、1回のめくりで画面幅ぶん進める。

```css
#reader { height: calc(100dvh - ヘッダー); overflow-x: auto; overflow-y: hidden; }
#reader .body { writing-mode: vertical-rl; height: 100%; }
```

モード2と同じく、枠側にサイズを与えないと要素が横に伸びて枠内スクロールにならない。

ページ送りは `scrollBy({ left: ±clientWidth })`。**`vertical-rl` でも `scrollLeft` は 0(右端＝先頭)から正方向(左＝後)へ進む**ため、「次ページ」は正方向。羅生門(約2万字)で6ページ分になった。

スクロールスナップは使っていない。めくりがボタン/キー操作で画面幅ぶん動かす方式のため不要だった。

## 読書画面のレイアウト

- 本文表示領域を最大化する
- モード切り替えUIを置く。常時表示か、操作時のみ表示かはプロトタイプで判断する

## プロトタイプの検証結果

羅生門の実データ(約2万字、ルビ129箇所、外字3箇所)を `src/pages/prototype.astro` で表示し、Chrome 152で確認した。当面はChromeを前提とし、他ブラウザの確認は後回しにする。

| 確認項目 | 結果 |
|---|---|
| モード2が段組みで実現できるか | **できる。** 制約する軸に注意(上記) |
| モード3のページ送り | **できる。** スクロールスナップは不要だった |
| ルビを含む行の縦書き表示 | 3モードとも破綻なし |
| モバイル幅(390×844)での表示 | モード2が意図通り動作 |

### 検証を受けて修正したこと

- **ルビの親文字を文字種の境界で判定する。** 当初は漢字だけを見ていたため、`ウヰスキー《whisky》` や `Whisky《ウィスキー》` が変換されず記法が画面に出ていた。正規表現の後方参照では正しく取れないため、行を1文字ずつ走査して単位の列を作り、そこにルビ・傍点を掛ける構造に組み直した
- **ルビの連鎖を分離する。** `申《さる》の刻《こく》下《さが》` で、ルビ付きの「刻」が後続ルビの親文字に飲み込まれ、「刻」のルビが失われていた。ルビ済みの単位は後続の親文字に含めない
- **空行を「間」として残す。** 場面転換の空行が消えていた
- **見出し注記を見出し要素にする。** `［＃「一」は中見出し］` が普通の段落になっていた。段組みで見出しの直後に列が切れないよう `break-after: avoid` を当てている
- **モードを切り替えても読書位置を保つ。** 以前は冒頭に戻っており、同じ箇所を別モードで見比べられなかった。段組みでは段落が複数の帯に分割され `getBoundingClientRect()` が全断片を覆う矩形を返すため、`elementFromPoint` で実際の描画位置から段落を引いている

### 残っている課題

- **外字が読書の妨げになる。** 面区点→Unicode変換が未実装のため、`目＋匡` のような字形説明がそのまま本文に現れ、3文字分の幅を占める。公式XHTML版を却下した理由でもあるので変換が必要。ただし変換表はJIS X 0213で数千エントリあり、エッジ関数のバンドルサイズに影響する。Unicodeに対応する文字が無い外字もある
- **読書位置の復元が2ブロックほど手前にずれる。** 読み飛ばしではなく少し戻る方向で、切り替え後は安定するため実用上は許容範囲
- **パーサーが本文全体を1行ずつ走査する。** エッジで毎リクエスト実行するため、長編でCPU時間上限に触れないか計測が必要([docs/design.md](./design.md) 参照)
- **モード切り替えUIを常時表示にするか、操作時のみ表示にするか**は未決
