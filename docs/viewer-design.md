# ビューア設計

[docs/requirements.md](./requirements.md) の「ビューア」の詳細設計。システム全体の設計は [docs/design.md](./design.md) を参照。

## 青空文庫記法パーサー

zipを展開しUTF-8に変換したテキスト([docs/design.md](./design.md) 参照)を入力とし、HTMLに変換する。

### 入力テキストの構造

実データ(羅生門、71行)で確認した構造。

```
 1  羅生門                          ← タイトル
 2  芥川龍之介                      ← 著者
 3
 4  ------------------------------  ← 記号説明ブロック開始
    【テキスト中に現れる記号について】
    《》：ルビ  ｜：ルビの付く文字列の始まりを特定する記号 …
16  ------------------------------  ← 記号説明ブロック終了
17
18  　ある日の暮方の事である。…      ← 本文
    :
58  底本：「芥川龍之介全集1」…       ← 底本情報
    入力：平山誠、野口英司
    校正：もりみつじゅんじ
```

- 冒頭のタイトル・著者はメタデータとして既に索引にあるため、本文からは除去する
- 記号説明ブロックは**ハイフンの連続行に挟まれる**。読者に見せる必要がないため除去する
- `底本：` で始まる行以降が底本情報。本文から分離し、別フィールドとして保持する

### 出力形式

**HTML文字列**として出力する。ルビは `<ruby>` タグ、傍点は `<em>` 相当の要素、といったHTMLの標準的な表現に落とし込み、縦書き・段組みといったレイアウトはCSS側で制御する。

- ブラウザ本来の描画機能(ルビ配置、行分割、段組み)をそのまま使えるため、実装量が小さい
- 読み方モードの違いは、原則としてCSSの切り替えで表現する
- HTMLでは表現しきれないレイアウト要求が出てきた場合に、構造化データ(JSON)出力への変更を検討する

### 対応する記法

実データで網羅性を確認しながら詰める。

- ルビ: `｜語句《ルビ》`(`｜` は語句境界が曖昧な場合に使われる)
- 注記: `［＃「対象」に傍点］` のような形式。傍点・強調・見出し・字下げ・改ページなどがある
- 外字注記: `※［＃…］` の形式。後述
- 本文中で直接使えない文字: `《》［］〔〕｜＃※`

### 外字の扱い

外字は `※［＃「てへん＋丑」、第4水準2-12-93］` のように、字形の説明と**面区点番号**で表現される。この番号からUnicodeのコードポイントを導き、**本物の文字として組む**。

公式XHTML版はこれを画像(`<img class="gaiji">`)で表現しており、フォントサイズに追従せず縦書きの行内で浮く。テキスト版を選んだ理由の一つがこれなので([docs/design.md](./design.md) 参照)、画像にフォールバックはしない。変換表を持てないコードポイントに遭遇した場合は、注記中の字形説明を代替テキストとして表示する。

### 底本情報の扱い

分離した底本情報(底本名・入力者・校正者など)は、本文とは別に作品ページのフッター等で表示する。クレジットの保持は青空文庫の慣習として期待されている([docs/requirements.md](./requirements.md) の「コンテンツに関する制約」参照)。

## 読み方モード

読者が読書画面で切り替えられる。選択内容は localStorage に保存する。

| モード | 文字の向き | 送り方 | 状態 |
|---|---|---|---|
| ページ | 縦書き | 1画面ずつめくる | 実装済み(既定) |
| 巻物 | 縦書き | 横スクロール(連続) | 実装済み |
| 縦段組 | 縦書き | 縦スクロール(帯を積む) | 設計済み・未実装。いまは出していない |
| ブログ | 横書き | 縦スクロール | 実装済み |

## ページモードの設計

### 何が問題か

「画面幅ぶんスクロールする」を、めくりだと思って実装していた。これはページではない。羅生門で実測すると3つの形で壊れる。

**1. 端で歩幅が変わり、往復で内容が変わる**

本文全体の幅7,742px、画面幅1,280px。割り切れないので最後の一歩だけ短くなる。

```
進む: 6462 → 5182 → 3902 → 2622 → 1342 → 62 → 0
                                        ↑ ここだけ62px(他は1280px)
戻る: 毎回1280px
```

歩幅が違うので、戻ると往路で見たページが出てこない。

| | 3歩目 | 5歩目 |
|---|---|---|
| 進んだとき | その髪の毛が、一本 | 成就した時の、安らか |
| 戻ってきたとき | 羅生門 | 「下人が雨やみを待っ |

**2. ページの境界で行が縦に割れる**

画面幅1,280px ÷ 行送り34.2px = **37.43行**。半端な0.43行が画面の端で縦に切られ、続きは次のページの端にまた半分だけ現れる。5ページ中3ページで発生した。

**3. 「いま何ページ目か」が存在しない**

位置がスクロール量という連続値でしかない。ページ番号がないので、`3 / 7` の表示も、指定ページへの移動も、位置の復元もできない。

**問題を一言でいうと、どこでページを切るかを決めていない。** 切れ目を決めずに「だいたい1画面ぶん動かす」ことでページのふりをしていた。

### 方式の比較

ページの切れ目を誰が作るかで3案ある。

| | 案A: 表示位置で切る | 案B: JSで詰め直す | 案C: CSS段組み |
|---|---|---|---|
| やること | 本文を横一列に組ませ、行送りの整数倍の位置で切って窓をずらす | 段落を測って1ページ分ずつ箱に詰め、溢れたら次の箱へ | `column-*` で「この大きさを埋めたら次へ」と指示する |
| 本文のHTML | 触らない | **切り分けて入れ直す** | 触らない |
| 分割するのは | 自分(座標計算) | 自分(測定ループ) | **ブラウザ** |
| コード量 | 中 | 大 | CSS 4行 |
| 一度に組む量 | 全文 | **現在のページだけ** | 全文 |

案Aは、いまの巻物モードが作っている「本文が横一列に伸びた状態」をそのまま切る案である。

### 採用: 案C(CSS段組み)

**理由: ページ分割はレイアウトの一部であり、ブラウザが持っている機能だから。**

行分割を自前で書く人はいない。どこで行が尽きるかも禁則もブラウザに任せている。ページ分割は同じ種類の問題を一段上でやっているだけで、CSSは `column-*` として公開している。自前で書けば、分割規則も再計算もすべてこちらの持ち物になる。

案Aは可否では負けていない。**改ページ注記も、余白を差し込んで押し出せば実現できる**(押し出し量はすべて行送りの整数倍なので、逐次ではなく一度に計算できる)。同じ理屈で見出しの取り残しも囲みの分断も回避できる。

しかしそれは、ブラウザの分割規則を1つずつ書き直すことに等しい。

| ブラウザが持っているもの | 案Aで自分が書くもの |
|---|---|
| どこでページが尽きるか | 座標を測って算出 |
| 強制分割(`break-before`) | 余白の押し出し量を計算 |
| 分割禁止(`break-inside`) | 要素が跨ぐか判定して押し出し |
| 見出しの取り残し(`break-after: avoid`) | 同上 |
| 孤立行(`orphans`/`widows`) | **段落の途中を切る必要があり、余白では作れない** |
| 文字サイズ変更時の再計算 | 全部やり直し |

最後の行が示すとおり、突き詰めると案Bに合流する。**案Aと案Cの違いは「できる/できない」ではなく、分割規則を誰が実装するかである。**

> 以前この設計では「縦書きでは段組みで帯を積めない」と結論していたが、**これは誤りだった**。当時の縦段組モードが `column-fill: balance` と不定な寸法で組まれていたのが原因で、仕組みの限界ではない。`column-fill: auto` と確定した寸法を与えれば正しくページに割れる。
>
> あわせて「案Aでは改ページ注記を守れない」とも書いていたが、これも誤り。上記のとおり余白の押し出しで実現できる。

### 段組みの指定

縦書きでは inline方向＝縦、block方向＝横。段は inline方向に積まれるので、**ページは縦に積まれる**。積まれる向きは書字方向で決まっており選べない(段組みの器を横書きにすると段に割れず、ただの横一列になる)。読者には窓の中の1ページしか見えないため、向き自体は問題にならない。

```css
.body {
  writing-mode: vertical-rl;
  block-size: 1136px;   /* 1ページの幅。ここで折り返す */
  inline-size: 553px;   /* 1ページの高さ。溢れた段は下へ積まれる */
  column-width: 553px;  /* 1段の高さ＝1ページの高さ */
  column-gap: 0;
  column-fill: auto;    /* 順に詰める。balance にすると均等割りされてページにならない */
}
```

ページkを出すには、窓を `k × ページの高さ` ずらす。

### 検証結果

| 項目 | 案A | 案C |
|---|---|---|
| 羅生門のページ数 | 7(末尾に59px余る) | **7(3,871px = 553×7 ちょうど)** |
| 往復で同じ内容 | ○ | ○ |
| 行が割れない | 整数倍の計算で保証 | **ブラウザが保証** |
| 改ページ指定 | 余白の押し出しを自作すれば可 | ○ `break-before: column` で7→9ページ、ずれ0px |
| 端数の始末 | 自前 | **不要(割り切れる)** |

実装後、案Cで組んだ画面でも確認した。

| 項目 | 結果 |
|---|---|
| ページ数 | 7。段の合計3,906px = 558 × 7 で端数なし |
| 行がページ境界で割れるか | 6ページとも割れなし |
| 進む・戻るで同じ内容か | 6ページぶんの先頭文字が完全に一致 |
| 文字サイズを変えたとき | 7→10→5ページと変わっても、読んでいた箇所が紙面に残る。元のサイズへ戻すと同じページ・同じ文字に復帰 |

### 読書位置の持ち方

**ページ番号を読書位置として持たない。** 文字サイズや画面幅が変わればページの割れ方が変わるため、ページ番号は表示のたびに変わる派生値でしかない。

これはEPUBの一般的な解き方に従う。EPUBには CFI(Canonical Fragment Identifier)という、読書位置を「文書内の何番目の要素の何文字目」で表す仕様がある。Readium の Locator も同様にレイアウト非依存である。しおり・注釈・読書位置はすべてこの座標で持つ。

| | 性質 | 用途 |
|---|---|---|
| 位置(段落番号＋段落内の文字位置) | レイアウト非依存 | 保存・復元・換算の基準 |
| ページ番号 | **レイアウト依存・毎回変わる** | いま画面を出すためだけ |

**位置 → ページ番号**
その文字にRangeを作り、矩形がどの段にあるかを見る。1回の測定で済む。

> ページをまたぐ段落に `getBoundingClientRect()` を使うと、複数ページにまたがる矩形が返る。縦段組モードで実際に踏んでいる。**文字1つのRangeで測る**か `getClientRects()` を使う。

**ページ番号 → 位置**
めくったら位置を更新するため逆変換も要る。そのページの先頭の文字を求める。全文走査は長編で重いが、**文字は読み順に沿って必ず後のページへ進む(逆戻りしない)ので二分探索が成立する**。68,000字でも十数回の測定で済む。

**いつ換算するか**
文字サイズ変更、画面リサイズ、モード切替、復帰時。手順は共通。

```
いまのページ先頭の文字を覚える
  → 組み直す(案Cならブラウザが行う)
  → その文字が入るページへ移動する
```

**アンカーのずれ**
ページ先頭に丸めるため、拡大・縮小を繰り返すと少しずつ手前へずれる(現行プロトタイプでも2ブロックほど手前にずれる現象が出ている)。**連続した調整のあいだはアンカーを取り直さない**ことで累積を防ぐ。読者がページをめくった時点で初めて更新する。

**換算は必須、保存は後回しでよい**
リサイズで読書位置を見失わないために、換算はページモードと同時に必要。localStorageへの保存は、換算ができていれば「アンカーを書く/読む」だけで足りるため後から追加できる。

### 進捗の表示

`3 / 71` のように**画面の枚数を出す**。文字サイズを変えると総数が変わる(実測: 68,851字が16pxで71ページ、22pxで122ページ)が、これを受け入れる。

Kindleが出している「ページ」は紙の版面のページ番号で、出版社の対応表を持つ本でのみ表示される。青空文庫には対応表がないので選べない。Apple Books・Kobo・日本の電子書籍アプリの多くは画面の枚数をそのまま出しており、総数が変わる方式も一般的である。

文字サイズ変更のUIを入れる際に、割合表示の併記を検討する。

### 長編への備え

案Cの構造的な制約は**全ページを一度に組むこと**である。ブラウザは全部の段を組んではじめて各ページの位置を知るので、5ページ目だけを組むことはできない。

実測では68,851字の組み直しが34〜43msだった(文字サイズを変えるたびに全ページ再計算しても同じ)。当面は問題にならない。

重くなった場合の答えは案Bへの乗り換えではなく、**本文を区切って区切りごとに組むこと**である。EPUBが章ごとに別文書へ分けてそれぞれ独立にページ割りしているのと同じ。青空文庫には ［＃改ページ］ と見出しがあるので、区切りはデータ側に既にある。

ただしその場合、組んでいない区切りのページ数が分からないため**総ページ数が出せなくなる**。総数を出し続けるなら全区切りを組む必要がある。

### 積み残し

- **めくりのアニメーション。** 段は縦に積まれるので、紙のように横へスライドさせるには別の細工が要る。瞬時に差し替えるなら不要
- **禁則。** `break-after: avoid`(見出しの取り残し)、`orphans`/`widows`(孤立行)をどこまで指定するか
- **底本情報。** 末尾に流れるので自然に最終ページへ入る。罫線がページ境界にかかる場合の扱いは未検討

## 縦段組モードの設計

### 何のためのモードか

**縦書きを、普通の縦スクロールで読めるようにする。**

巻物は横スクロールなのでマウスホイールが素直に効かず(Shiftが要る)、ページは送り方を覚える必要がある。縦段組はホイールもトラックパッドもスマホの縦フリックも、そのまま使える。

### 仕組みはページと同じ

ページモードで使っている段組みがそのまま使える。**違いは見せ方だけ**である。

| | 段の見せ方 |
|---|---|
| ページ | 1帯だけ窓に映し、めくって差し替える |
| 縦段組 | 積まれた帯をそのまま縦スクロールで見せる |

> 以前この節には「現在の縦段組は `column-fill: balance` と不定な寸法のせいで帯が揃わない」とだけ書いていた。指定の問題という点は正しいが、**それを直すだけでは足りない**。下記の固有の問題がある。

### このモード固有の問題

**縦書きの帯は、途中で切れると1行も読めなくなる。**

```
横書き(ブログ)              縦段組
┌──────────┐              ┌──────────┐
│  行が切れる  │            │ ┊ ┊ ┊ ┊ ┊│ ← 画面の外
├──────────┤ 画面        ├─┊─┊─┊─┊─┊┤
│ 読める行     │            │ ┊ ┊ ┊ ┊ ┊│   全部の行が
│ 読める行     │            │ ┊ ┊ ┊ ┊ ┊│   途中で切れる
└──────────┘              └──────────┘
残りの行は読める            どの行も読めない
```

横書きなら切れるのは端の行だけで残りは読める。縦書きの帯は**全部の行が同じ高さで切れる**ため、半端な位置で止まると何も読めなくなる。

3モードのうちこれが起きるのは縦段組だけである。ページは1帯がぴったり収まり、巻物は行が常に画面の高さいっぱいにあるため起きない。

### 対策: 常に1帯以上が丸ごと見えるようにする

画面の高さ H、帯の高さ h、帯の間隔 g のとき、

```
2h + g ≤ H
```

を満たせば、**どこでスクロールを止めても必ずどれか1帯が丸ごと画面に入る**。帯の始まりは h+g ごとに並ぶので、画面が帯2つぶんの高さを持てば、切れていない帯が最低1つは入るためである。

**却下した案: 帯を画面いっぱいにして、スクロールが止まったら帯単位に吸い付かせる。**
読めなくなる問題は解けるが、それだと**ページモードとの違いが操作方法だけ**になる。このプロジェクトは読み方を比べるのが目的なので、性格の近いモードを2つ持つ意味が薄い。

上記の対策なら3モードの性格がはっきり分かれる。

| | 1画面に見える量 | 字詰め | 送り方 |
|---|---|---|---|
| ページ | 約620字 | 31字 | 離散 |
| **縦段組** | **約1,260字** | **18字** | **連続** |
| 巻物 | 約1,000字 | 31字 | 連続(横) |

字詰め18字は新聞の段組み(11〜15字)に近く、1画面あたりの文字数はページの倍になる。密度の高い読み方として明確に別物になる。

### 寸法の決め方

パラメータは**1画面に何帯見せるか(n)**だけ。既定は n = 2。

```
帯の高さ = floor((画面の高さ − 間隔×(n−1)) ÷ n ÷ 字送り) × 字送り   … 字詰め
帯の幅   = floor(使える幅 ÷ 行送り) × 行送り                        … 行数
```

ページモードと同じく、高さは字送りの、幅は行送りの整数倍に丸める。半端が残ると行末や紙面の端に文字の入らない隙間ができる。

### 帯の間隔

1〜2行ぶん空ける。ページモードは窓で1帯だけ見せるため `column-gap: 0` にしたが、縦段組では**切れ目が見えること自体が必要**になる。

### スクロールさせるのはページ全体

`#reader` の高さを全帯ぶんにして、ブラウザのページスクロールで読ませる。ホイールもスペースキーもスクロールバーも、普通のWebページと同じに効く。

`#reader` の中だけをスクロールさせる形(巻物と同じ)も作れるが、キーボードでの送りが効かなくなり、スマホの慣性スクロールも崩れやすい。採らない。

**帯の数は組んでみないと分からないので、二度組む。**

```
1回目: 高さを1帯ぶんにして組み、溢れた分から全体の高さと帯の数を知る
2回目: その高さと帯の数を入れて組み直す
```

増えるのは組み直し1回(68,851字で約40ms)で、初回とリサイズ時にしか起きない。帯の数は1回目で判明しているので、2回目は `column-width` の目安ではなく `column-count` で確定させる。丸めで段が増減する余地をなくすため。

### 操作

クリックでの送りは入れない。縦スクロールが主なので左右クリックは合わない。

### 読書位置

ページモードの換算(本文中の位置で覚え、組み直したあとに測り直す)がそのまま使える。ページ番号の代わりにスクロール量になるだけである。

## モードごとに実装を分ける

現在は1つの `Reader.astro` に全モードのCSSが同居し、共通の基底ルールを各モードが上書きする形になっている。**上書き漏れがそのまま不具合になる**構造で、実際に2件出した。

- 縦書き用の下寄せ指定が共通の `margin-bottom` と噛み合わず、著者名の下に3文字分の空きができた(物理プロパティが縦書きで別の向きに効いていた)
- 本文の文字サイズを変えたとき、横書きのタイトルまで小さくなった

ページモードは他モードにない**切り取り窓の入れ物**が要るため、markupから異なる。同居させると差はさらに広がる。

```
components/reader/
  Reader.astro        モード選択と、本文HTML・扉・底本を持つだけ
  PageMode.astro      ページ: 測らなくても決まるCSS
  ScrollXMode.astro   巻物
  BlogMode.astro      ブログ
lib/reader/
  mode.ts             mount / unmount / resize の型
  page.ts             ページ: 段組みの寸法、位置とページ番号の換算、めくり
  scroll-x.ts         巻物
  blog.ts             ブログ
```

各モードが自分のmarkup・CSS・挙動を閉じて持ち、**モード間で共有するのは本文のHTMLだけ**とする。共通の基底CSSを置かないので上書き漏れが起きない。

モードは `mount` / `unmount` / `resize` を実装する。**`unmount` があるのは、モードが自分で加えたものを自分で戻すため。** 共通の関数の中で「このモードでなければ消す」と分岐していると、モードが増えるたびに分岐が育つ。ページモードは窓の要素を作って本文をその中へ移すので、戻す処理もここに書く。

実装は自動登録ではなく明示的に並べる。読み込み順に依存して壊れるのを避けるため。

代償は扉(作品名・著者名)や底本の体裁がモードごとに重複することだが、その共通化こそが上記2件の原因なので、重複させる方を採る。

モード切替時は本文要素を現在のモードの入れ物へ移す。位置は換算の仕組みで保つ。

## 読書画面のレイアウト

- 本文表示領域を最大化する
- モード切り替えUIを置く。常時表示か、操作時のみ表示かはプロトタイプで判断する

## 検証の記録

羅生門(約2万字、ルビ129箇所、外字3箇所)と大菩薩峠 第一巻(68,851字)の実データを Chrome 152 で確認した。当面はChromeを前提とし、他ブラウザの確認は後回しにする。

| 確認項目 | 結果 |
|---|---|
| 縦書きの行送り | `line-height` と一致し全行一定(18px × 1.9 = 34.2px)。ルビがあっても変わらない |
| CSS段組みで縦書きをページに割れるか | **割れる。** 羅生門で 3,871px = 553 × 7 と端数なし。`column-fill: auto` と確定した寸法が要る |
| 強制改ページ | **効く。** `break-before: column` で7→9ページ、指定箇所のずれ0px |
| 段が横に積めるか | **積めない。** 段組みの器を横書きにすると段に割れず、ただの横一列になる |
| 文字サイズ変更の組み直し | 68,851字で34〜43ms。同じサイズに戻すと同じページ数になり再現性がある |
| 画面幅ぶんスクロールする方式 | **ページとして成立しない。** 端で歩幅が変わり往復で内容が変わる。行も割れる |
| ルビを含む行の縦書き表示 | 破綻なし |
| モバイル幅(390×844) | 縦スクロール系は意図通り動作。UIは別途検討 |

### 検証を受けて修正したこと

- **ルビの親文字を文字種の境界で判定する。** 当初は漢字だけを見ていたため、`ウヰスキー《whisky》` や `Whisky《ウィスキー》` が変換されず記法が画面に出ていた。正規表現の後方参照では正しく取れないため、行を1文字ずつ走査して単位の列を作り、そこにルビ・傍点を掛ける構造に組み直した
- **ルビの連鎖を分離する。** `申《さる》の刻《こく》下《さが》` で、ルビ付きの「刻」が後続ルビの親文字に飲み込まれ、「刻」のルビが失われていた。ルビ済みの単位は後続の親文字に含めない
- **空行を「間」として残す。** 場面転換の空行が消えていた
- **見出し注記を見出し要素にする。** `［＃「一」は中見出し］` が普通の段落になっていた
- **縦書きでは論理プロパティで指定する。** 著者名の下に3文字分の空きができていた。共通指定の `margin-bottom` が、縦書きでは本文との間隔ではなく著者名の真下に効いていたため。物理プロパティ(`top`/`bottom`/`left`/`right`)は書字方向で向きが変わるので、両方向で使う指定には使わない

### 残っている課題

- **外字が読書の妨げになる。** 面区点→Unicode変換が未実装のため、`目＋匡` のような字形説明がそのまま本文に現れ、3文字分の幅を占める。公式XHTML版を却下した理由でもあるので変換が必要。ただし変換表はJIS X 0213で数千エントリあり、エッジ関数のバンドルサイズに影響する。Unicodeに対応する文字が無い外字もある
- **読書位置の保持を一度廃止した。** モード切替時に位置を保っていたが、2ブロックほど手前にずれる問題があり、ビューアの構造が固まる前の実装だったため取り外した。上記「読書位置の持ち方」に沿って作り直す
- **モード切り替えUIを常時表示にするか、操作時のみ表示にするか**は未決
